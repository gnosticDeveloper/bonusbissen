# Onboarding

## Recorrido

Cinco diapositivas: Cuenta y negocio → Plan → Mercado Pago → Sucursal → Programa de puntos. El nombre del negocio se pide después de crear o ingresar a la cuenta. La recuperación requiere login ADMIN según los contratos existentes. El root consume `PlanSelectionScreen` de `./pago/plan-selection-screen` y `PaymentScreen` de `./pago/payment-button`, ambos con `{ expectedOrganizationId, onContinue, disabled }`. Cada callback vuelve a consultar el estado backend antes de avanzar. Los screens de billing conservan su flujo de consultas y autorización; su copy distingue autorización de cobros de un pago confirmado, sin promesas de límites o prestaciones por plan.

No hay card común envolviendo las slides: Organización usa una columna centrada y angosta; Plan dispone de ancho para sus cards; Mercado Pago conserva sus columnas; Sucursal y Programa usan ancho de formulario. Sólo desde `lg` se amplía el layout de `max-w-2xl` a `max-w-6xl` y se compacta el espaciado exterior. En mobile se conservan anchos, padding y separación existentes. No se fija la altura ni se recorta contenido: el documento hace scroll vertical cuando sea necesario. El root no ofrece botones «Actualizar estado», consultas de facturas ni enlaces de escape a Mi negocio o gestión de billing. Sólo los errores ofrecen reintento contextual de consulta. Mi negocio se abre mediante finalización verificada. El footer de logout del root aparece fuera de Plan/MP; esos screens ya tienen su propio footer. `leaveOnboarding` revoca ambas sesiones mediante el helper existente, elimina sus cookies y expira el hint, sin borrar recursos ni la preferencia local.

Billing utiliza autenticación independiente. `adminOrganization` valida el contexto específico del onboarding y no es un helper genérico de billing. Sucursal, programa y finalización verifican en sus Server Actions que `GET /organization` informe un `billingPlanName` no vacío y `mercadoPagoSubscriptionStatus === "authorized"`. El response no incluye un ID de plan: no se inventa ni se infiere ID, precio o permisos a partir del nombre. Es un requisito de este recorrido frontend, no una política global nueva del backend. Ausencia o cualquier otro estado bloquean la configuración. No se exige una factura pagada: las cuotas pueden cobrarse en el futuro. El progreso local no autoriza cobros ni acredita pagos.

### Contratos TypeScript

- `OnboardingState.userId: string | null`: identidad verificada con sesión y backend. No se obtiene de localStorage ni de una cookie de progreso. Sin identidad verificada, el cliente no lee ni escribe progreso local.
- `finishOnboarding(): Promise<FinishResult>` devuelve `{ error: string }` o `{ error: null, userId: string, destination: string }`. La navegación se realiza en el cliente después del intento de limpieza local. El destino se construye en servidor después de verificar el negocio, la suscripción autorizada, una sucursal activa con programa vinculado y un JWT firmado del administrador actual con `sf` igual a esa sucursal. No hay un endpoint nuevo de completion: se verifica la configuración persistida mediante los GET existentes.
- `OnboardingProgressStore`: interfaz async `load(userId)`, `save(userId, progress)` y `clear(userId)` en `client/lib/onboarding-progress.ts`. `createOnboardingProgressStore()` selecciona la implementación predeterminada y serializa las operaciones. El componente sólo conoce esta fábrica y la interfaz; también acepta un adapter opcional `progressStore` para pruebas o integración.

## Persistencia y reanudación

LocalStorage guarda solamente una preferencia de navegación, nunca habilita etapas. Clave: `onboarding-progress:v3:{userId codificado}`. Sólo guarda versión 3, usuario, organización y paso (0–4). Al leer v2 se migran 0→0, 1→2, 2→3 y 3→4; desde v1 se migran 0→0, 1→3 y 2→4. La lectura prioriza v3, luego v2 y finalmente v1. Al guardar v3 se eliminan las claves anteriores; al finalizar se limpian las tres versiones. No guarda campos de formularios, contraseñas, tokens ni datos de pago. La escritura usa una lista explícita de campos permitidos.

Antes de guardar se espera la restauración, evitando sobrescribir el paso almacenado al montar. Cada cambio de paso se persiste. La restauración sólo acepta el mismo usuario y organización y limita el paso según los recursos verificados por el backend. `availableStep` devuelve 0 sin organización verificada, 1 sin `billingPlanName`, 2 sin autorización, 3 sin sucursales y 4 en los demás casos, en ese orden. Incluso una organización autorizada con recursos existentes vuelve a Plan si backend no informa un nombre de plan. Un paso local nunca evita estas restricciones. `minimumStep` impide retroceder a crear un negocio ya verificado (mínimo 1), a cuenta/plan/pago después de autorización (mínimo 3), o a crear sucursal si ya existe (mínimo 4). Sin plan, el mínimo es 1 incluso con autorización y sucursales existentes: el gate de plan prevalece. Antes de la autorización se puede volver de Mercado Pago a revisar Plan. Tanto restauración como navegación y botón Volver usan los mismos límites. `/billing` mantiene su retorno a `/onboarding/pago`; «Continuar configuración» vuelve a `/onboarding`, que consulta backend de nuevo. No se usa query ni almacenamiento como evidencia de autorización. También se refresca el estado al continuar desde cada diapositiva o avanzar desde el navegador de pasos. Se restaura sólo al montar o cambiar la identidad/organización, no después de cada refresh o mutación del mismo contexto. Las acciones exitosas mantienen su avance explícito; ante fallos, el paso actual se limita según los recursos verificados. Una restauración lenta no sobrescribe navegación ni resultados de acciones posteriores, y una respuesta de otro contexto se descarta. Las operaciones async se serializan, para que una escritura pendiente no reaparezca después del borrado.

La cookie `onboarding_progress` es sólo un hint temporal con IDs, httpOnly, SameSite=Lax, Secure en producción, siete días y path `/onboarding`. Su owner se compara con las identidades de sesión antes de usarla. Una cookie ajena no permite exponer recursos ni escribir en otro negocio. Sin cookie válida, una sesión ADMIN y `GET /organization` permiten recuperar el negocio; la cookie no autoriza nada por sí sola.

El primer ingreso, la cuenta recién creada y la organización pendiente del primer login admin no muestran un error de sesión: no tener sesión admin todavía es normal. Una sesión realmente expirada o no verificable sí informa reingreso o reintento. Una cookie de otra cuenta no bloquea crear una organización; sólo se reemplaza tras confirmar el alta en backend para el usuario actual. Para retomar un negocio con una cookie ajena se requiere selección explícita y login ADMIN verificado.

`/onboarding?ingresar=1` abre un formulario de reingreso independiente del paso calculado. `page.tsx` espera `searchParams` y pasa `recoverAccount` al cliente; el parámetro sólo abre el formulario, nunca autoriza etapas. Los enlaces de recuperación en pago y planes usan este destino, y el root permite reingresar desde cualquier paso. Con negocio verificado o hint propio no se ofrece crear ni elegir otro negocio. Sin identidad verificada no se muestra el progreso de la cuenta anterior. «Ya creé un negocio» permite buscar el negocio cuando no hay un hint propio disponible. Las acciones de configuración no agregan renovación propia: el proxy gestiona ambas áreas antes de cada GET/POST de onboarding. La expiración de una sesión opcional no fuerza un redirect; las acciones comprueban el acceso necesario para cada operación. Si las sesiones customer y dashboard pertenecen a personas distintas, se exige reingreso con la misma cuenta.

Al crear o recuperar una sucursal activa, `ensureOnboardingStorefront` consulta `GET /staff`, identifica al administrador activo por el `sub` verificado y agrega sólo la asignación faltante mediante `POST /staff/{id}/storefronts`. No crea otro staff, cambia roles ni quita otros locales. `attach` no emite JWT: después se llama siempre a `POST /auth/storefront` mediante `selectStorefront`, incluso si el JWT actual ya tiene ese `sf`. Se envía el refresh dashboard actual como `Cookie: bb_rt=...` para que `AuthController` actualice el contexto de la sesión backend a la misma sucursal; no se rota ni reemplaza esa cookie desde la selección. El JWT devuelto se verifica con `checkSession` (firma, identidad, rol y `sf`) antes de persistirlo con las opciones existentes y actualizar la lista de locales. El helper vuelve a comprobar la sesión persistida. Los reintentos secuenciales reutilizan la sucursal y la asignación confirmadas, incluso tras perder sus respuestas.

Al finalizar, el servidor verifica de nuevo los recursos, asegura la asignación y selección de una sucursal con programa activo y comprueba otra vez el `sf` firmado antes de expirar el hint. Si falla, no devuelve destino ni borra el progreso. El cliente espera `clear(userId)` antes de `router.push(destination)`. Si el backend rechaza el cierre no se borra el progreso. Si falla el borrado local, se informa el fallo y se navega igualmente después del intento: el almacenamiento opcional del navegador no bloquea un cierre confirmado por backend. Puede quedar un hint local obsoleto, que se volverá a validar contra sesión y backend al regresar. Si localStorage no está disponible al cargar/guardar, se informa sin impedir que los recursos se guarden en backend.

## Límites

- Los límites de navegación se aplican dentro del onboarding. No se agrega una política global de acceso a la configuración del panel ni se modifican los permisos del backend.
- Los recursos se consultan sin caché. Sucursal y programa ya existentes se reutilizan para evitar altas duplicadas en reintentos secuenciales.
- No hay claves de idempotencia ni coordinación entre pestañas/dispositivos. La garantía de exactamente una creación requiere soporte backend.
- Si se pierde la respuesta de creación de organización antes de guardar el hint, se debe usar «retomar». El backend rechaza una nueva creación para quien ya es staff.
- La selección y asignación automáticas pertenecen a las acciones del onboarding; el destino sigue siendo `/d/{id}/mi-negocio` con el negocio verificado. No se fabrica ni modifica el JWT, ni se cambia Java para emitirlo.
- No se persisten campos sin enviar. La primera sucursal es física: el formulario muestra siempre AddressSelector, que sigue usando georef. La acción exige dirección, localidad y provincia, ignora el campo `online` recibido y fuerza `online: false` en el POST, aunque se envíe `online=true` manualmente.

## Validación

Desde `client`, ejecutar las suites por separado porque la suite de acciones reemplaza módulos del runtime Next:

```sh
bun test ./app/onboarding/onboarding.test.js
bun test ./app/onboarding/storefront-session.test.js
bun test ./lib/onboarding-progress.test.js
bun test ./app/onboarding/pago/billing.test.js
node node_modules/typescript/bin/tsc --noEmit --incremental false
```

Cobertura: autorización/owner, expiración, recuperación sin cookie, reintentos, vínculo de programa, destino de cierre, aislamiento local por usuario, registros corruptos, allowlist, migraciones v1/v2→v3, retorno autorizado, revocación de plan/suscripción, bloqueo de setup/cierre sin plan aun estando autorizado, restauración limitada por backend, almacenamiento bloqueado y orden save → clear → navegación. La prueba de persistencia verifica que el gate de plan precede a checkout y recursos posteriores; las acciones de checkout permanecen a cargo de billing.

Guías Next.js consultadas en la versión instalada (16.3.4):
- `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/page.md`: `searchParams` asíncrono en páginas de servidor.
- `node_modules/next/dist/docs/01-app/01-getting-started/03-layouts-and-pages.md`: layouts anidados y su persistencia entre navegaciones.
- `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-router.md`: navegación cliente con destino verificado y diferencias respecto de `refresh()`.

La suite de persistencia incluye límites mínimos/máximos, revisión de plan antes de autorización, restauración de pasos antiguos y revocación del plan con recursos existentes. Las suites de acciones y sesiones se mantienen en sus alcances separados. `storefront-session.test.js` usa `checkSession` real con claves ES256 exclusivas de prueba: verifica firma, expiración, identidad, rol y `sf`, el envío del refresh actual aun con el mismo `sf`, y que sólo se escriban las cookies de acceso y lista de locales. No sustituye una prueba E2E de renovación contra Java.

Validación previa del refactor: 52 tests de onboarding, 16 de persistencia y 17 de billing pasaron, ejecutados en procesos separados. TypeScript (`tsc --noEmit --incremental false`) y `git diff --check` pasan. ESLint sobre los archivos TypeScript del alcance falla al cargar la regla `react/display-name`: `contextOrFilename.getFilename is not a function` (ESLint 10.10.0 / plugin React); no se modifican dependencias para resolverlo.

Validación de selección y mensajes de sesión: 76 tests del root y 9 de sesión pasan en procesos separados; también pasan TypeScript (`tsc --noEmit --incremental false`) y `git diff --check`.

Validación integrada: 155 pruebas pasan (30 proxy, 76 acciones, 9 selección de sucursal, 18 persistencia y 22 billing/coordinación), en procesos separados para aislar mocks. TypeScript, build de producción y `git diff --check` pasan. ESLint continúa bloqueado por la incompatibilidad indicada arriba. No se ejecutó E2E contra backend ni cobro real; la adaptación visual requiere revisión manual en navegador.
